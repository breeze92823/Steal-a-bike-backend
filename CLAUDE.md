# Steal a Bike — BACKEND (game server)

Frontend (3D client) lives at `../Steal-a-bike`. Colyseus + Mongo. Integration follows docs.bloxity.io (REST endpoints, matchmaker) and hosting.bloxity.io/docs (deploy, matchmaker connect).

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { userId, username, pfp, token, avatar, pose, loadout })`). It is the shared hub: everyone sees everyone. A room is one hub of `PLOT_COUNT` (7) bases, so `ROOM_MAX_CLIENTS` is 7 and an eighth player gets a new room. On join the server gives each player the lowest free plot (roster `plot`, kept through a reconnect, freed when they leave). Room metadata `{ mode: "hub" }` for the platform's server browser. Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests (`guest-` ids) are never saved. `/health` for Legion; `/monitor` and the playground are dev-only.
- **Identity** (`src/auth.ts`, after Lumber-empire): in production (`NODE_ENV=production`, set by Legion) the client's Bloxity token is checked with `POST {BLOXITY_API_URL|https://api.bloxity.io}/v1/auth/game-token/verify` and the id Bloxity names is the account; no token, a refused one, an outage or a `dev-` id all mean guest. Outside production the sent id is trusted (local play, tests). Answers are cached by a hash of the token.
- **Slug**: `GAME_SLUG = "steal-a-bike"` in `src/constants.ts` (the client's `GAME_SLUG`); the hosting env `BLOXITY_GAME_ID` wins when set.
- The client keeps NO progress in the browser: this server's Mongo doc is the player's only save (daily/fuse also keep a localStorage copy for offline play). A guest's progress lasts the page only.
- Messages client -> server: `saveProgress` (the whole snapshot, debounced client-side), `identify` (`{ userId, username, pfp, token }` after a sign-in/out mid-session), `pose` / `loadout` / `setAvatar` (presence), `leaderboard` (ask for the lists again). Server -> client (private): `progress` (the saved doc, sanitized), `noProgress` (new account, guest, or no database: the client keeps its fresh state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten), `leaderboard`. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted.
- Saved progress (`PlayerDoc`, client `src/net.js` `progress()` + each module's `registerStore` snapshot, client `src/stores.js`): `cash`, `gems`, `speed` (the bike counter), `income` ($/s), `treadmill` (level), `bikes[]` (names, duplicates kept), `placed[]` (bikes parked in the base, slot order), `found[]` / `claimed[]` (Bike Index), `trails[]` / `trail` (equipped must be owned), `fuse`, `dailyClaimed` / `dailyLast`, `playtime`, `lastSeen`. A contract change goes in both projects (`src/constants.ts` bounds must cover the client's catalogs; bike names match `BIKE_NAME_PATTERN`).
- **Roster / presence** (`src/presence.ts`, `PlayerState`): `username`, `signedIn`, `pfp`, `x/y/z` (feet, m), `yaw`, `speed`, `state` (0 on foot, 1 on a bike, 2 walking a bike), `trail`, `bike`, `avatar` (Bloxity look JSON `{ equipped, proportions, skin }`, at most `AVATAR_MAX_LEN`, never parsed: skin sync). Ids only, never URLs, except the skin texture URL the SDK itself returns. Client draws them in `remotePlayers.js`.
- **Leaderboards** (`src/leaderboard.ts`): the hub's MOST CASH board = top `LEADERBOARD_SIZE` (50) saved players by `cash` (and `speed`), one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS` (60 s), each player's own rank = countDocuments(stat > theirs) + 1 (null for guests). Sent after each load and every minute. `connectDb` creates a descending index per stat.
- **Bloxity's trophy boards** (`src/platformBoards.ts`): saved cash / speed are queued and reported every 30 s to `{BLOXITY_API_URL}/v1/leaderboards/hosted/{BLOXITY_GAME_ID}/report` as `legion_<id>` with `PLATFORM_BOARDS` (must match the client's `LEADERBOARDS`; Most Cash first). No-op without `BLOXITY_REPORT_TOKEN`.
- **Room directory** (`src/legion-room-reporter.ts`): pushes this pod's rooms to the matchmaker every 2 s (`MATCHMAKER_REPORT_URL`, `BLOXITY_REPORT_TOKEN`) so Open Rooms, friend joins and join-by-id work across pods. No-op without those env vars.
- **Plausibility** (`src/plausible.ts`): saves are still client-authoritative, but the server counts the seconds it has seen an account play (`earnSeconds`, server clock, doc field) and does not store a `cash` / `speed` above what that time can pay (`CASH_*` / `SPEED_*` in constants.ts, derived from the client's economy with slack). A refused number keeps its stored value, the rest of the save goes through. It stops forged absurd numbers on the boards, not a determined cheat within the generous ceiling; a real fix is a server-side economy.
- **Gems** (`src/gems.ts`): `POST /webhooks/gems` (set as the game's webhook in the Bloxity dashboard) grants `GEM_PACKS[sku]` gems, idempotent by `transactionId` (`purchases` collection, safe across pods), checks `x-legion-webhook-secret` against `LEGION_WEBHOOK_SECRET`, 2xx to confirm / 4xx to refuse (refund). `gems` is server-owned: `saveProgress` never carries it; the room tells the player with `gems` { gems }, a `progress` carries the balance. Add SKUs to `GEM_PACKS` as products are created.
- **Bases** (`presence.ts` `applyBase`, `test/Roster.test.ts`): roster `plot` (-1 = none), `floors` (1..`BASE_FLOORS_MAX` = 3), `placed` (parked bike names, slot order, "|"-joined, names checked like a save's, at most `PLACED_MAX`), `treadmill` (level). Message `base` { floors, placed: [], treadmill }; the join options may carry `base`. Saved: `floors` (sanitize.ts) next to `placed`.
- **FREE GIFT!** (`src/adReward.ts`, `test/Guards.test.ts`): message `adReward` { rewardToken } (from a finished Bloxity rewarded ad) is checked with `POST {BLOXITY_API_URL|https://api.bloxity.io}/v1/ads/reward/verify` { gameSlug, rewardToken } and answered privately with `adReward` { ok, reason?: "cooldown" | "invalid", readyAt, serverTime }; the client pays +100 Speed only on ok. At most once per `GIFT_COOLDOWN_MS` (5 min) per account: `giftAt` (doc, server-written) and the per-session `giftReady`; `progress` carries `giftReadyAt`. An outage is a no.
- Roster also has `uid` (checked account id: Bloxity chat messages name their sender by it) and `emote` (`"<id>#<n>"`, message `emote`).
- Env (all optional locally, see `.env.example`): `MONGODB_URI`, `CLIENT_ORIGIN`, `PORT`, `NODE_ENV`, `BLOXITY_GAME_ID` (Legion injects these), `BLOXITY_API_URL`, `BLOXITY_REPORT_TOKEN`, `MATCHMAKER_REPORT_URL`, `LEGION_WEBHOOK_SECRET` (from the game's dashboard).
- Not done: a server-side economy (see Plausibility), a Gems shop UI in the client (the helper `bloxity.buyGems(sku)` and `net.onGems` exist; the trail / treadmill gem prices still only toast).
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` (never `seatCap`: the SDK docs forbid it) read from `src/constants.ts` (= `PLOT_COUNT`, 7; keep it 2-100 for party play). Needs repo var/secret `LEGION_GAME_ID` (= `steal-a-bike`) and secret `LEGION_DEPLOY_TOKEN`. The GHCR package must be made public once.
